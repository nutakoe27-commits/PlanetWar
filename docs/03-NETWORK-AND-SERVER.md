# 03 — Сеть и сервер

Это ключевой документ проекта. Здесь решается задача «захват множества планет
вплоть до бесконечности» и обходится проблема, об которую разбилась поздняя игра
Stellaris.

## Как достигается «бесконечность планет»

Буквальная бесконечность невозможна: состояние надо где-то хранить. Но достижимо
то, что для игрока неотличимо от бесконечности. Три механизма:

### 1. Галактика не хранится — она вычисляется

Содержимое системы выводится детерминированно из координат и сида сезона:

```
system_content = generate(hash(season_seed, coord_x, coord_y))
```

Отсюда: звезда, число и классы планет, слоты, залежи ресурсов, аномалии.

Адресное пространство — 2⁶⁴ систем. **До первого касания игроком система не
занимает ни одного байта в базе данных.** Клиент, зная сид, генерирует
визуальное наполнение локально — по сети идут только различия.

### 2. В базу пишутся только дельты от процедурного состояния

Запись появляется, когда игрок что-то изменил: колонизировал, построил,
застолбил, разрушил. Хранится не «планета», а **разница между планетой из
генератора и её текущим состоянием**.

Нетронутый фронтир — это ноль строк в БД при любом размере галактики.

### 3. LOD симуляции

Системы классифицируются каждую секунду по трём уровням:

| Уровень | Условие | Тик |
|---|---|---|
| **Горячая** | Есть онлайн-игрок, идёт бой, идёт осада | 10 Гц, полная симуляция |
| **Тёплая** | Владение игрока без активности, стоят конвои | 1 Гц, упрощённая |
| **Холодная** | Всё остальное | **0 Гц** — не тикает вообще |

Холодные системы используют **ленивое досчитывание**: у каждой хранится метка
времени последнего обновления. Когда состояние понадобилось — при заходе игрока,
при отправке снапшота, при подсчёте престижа — накопления считаются одной формулой
за прошедший интервал:

```
resources += rate * (now - last_update)
```

Вместо трёх суток тиков — одно умножение.

Такое досчитывание корректно, потому что экономика на слотах линейна на интервале
без событий. Любое событие (постройка, атака, смена специализации) переводит
систему в тёплое состояние и фиксирует новую метку времени.

### Что из этого следует

> **Нагрузка на сервер масштабируется от числа онлайн-игроков, а не от размера
> вселенной.**

Игрок может владеть 5000 планет — если он ими не занимается прямо сейчас, они
стоят серверу столько же, сколько нетронутый фронтир. Именно этого не хватило
Stellaris, где ежедневный тик проходил по всем популяциям во всей галактике
независимо от того, происходило ли там что-нибудь.

## Топология сервера

```
                    ┌─────────────────┐
   Клиенты ────────▶│     Gateway     │  TLS, аутентификация, роутинг,
                    │                 │  ограничение частоты команд
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        ┌──────────┐   ┌──────────┐   ┌──────────┐
        │ Sim-нода │   │ Sim-нода │   │ Sim-нода │   регион галактики на ноду
        │ регион A │   │ регион B │   │ регион C │
        └────┬─────┘   └────┬─────┘   └────┬─────┘
             └──────────────┼──────────────┘
                            ▼
                 ┌─────────────────────┐
                 │ PostgreSQL + Redis  │  дельты, снапшоты, журнал команд
                 └─────────────────────┘
                            ▲
                 ┌─────────────────────┐
                 │  Season / Meta      │  рейтинг, престиж, магазин косметики,
                 │                     │  аккаунты
                 └─────────────────────┘
```

### Шардинг по регионам, а не по игрокам

Регион — связная группа систем. **Границы регионов проводятся по редким
гиперлиниям**: генератор галактики специально ищет разрезы графа с минимальным
числом рёбер и режет по ним. Чем меньше рёбер пересекает границу, тем меньше
межнодового трафика.

При пересечении границы сущность передаётся на соседнюю ноду — тот же приём, что
у EVE Online, где каждая солнечная система живёт в своём процессе
([разбор архитектуры](https://highscalability.com/7-sensible-and-1-really-surprising-way-eve-online-scales-to/)).

Регионы перебалансируются между нодами по нагрузке; горячий регион может получить
ноду целиком.

### Почему у нас не нужно замедление времени

EVE при массовых боях включает Time Dilation и замедляет симуляцию вплоть до 10%
скорости — тысячи пилотов в одной системе иначе кладут ноду.

У нас этой проблемы нет по конструкции: **бой разрешается по флотам, а не по
кораблям** (см. [01-GAME-DESIGN.md](01-GAME-DESIGN.md)). Сражение 500 флотов стоит
примерно столько же, сколько 500 обычных тиков — независимо от того, 10 кораблей в
каждом флоте или 10 000. Отдельные корабли существуют как числа в составе флота, а
не как сущности симуляции.

Это прямое следствие решения об автоматическом разрешении боя и одна из главных
причин, по которым оно принято.

## Тик и планировщик

- Базовая частота горячих систем — 10 Гц
- Тёплых — 1 Гц
- Холодные не тикают
- Переклассификация — раз в секунду

Внутри тика системы обрабатываются джоб-системой параллельно; порядок применения
результатов детерминирован (по индексу региона, затем по индексу системы), чтобы
многопоточность не ломала воспроизводимость.

## Репликация клиентам

### Area of Interest

Игрок получает состояние:

- систем, где у него есть активы
- систем в радиусе N прыжков от его активов
- систем, покрытых его сенсорами и разведкой
- систем, разделённых союзниками по альянсу

Всё остальное **не отправляется вообще**. Это одновременно и оптимизация трафика,
и античит: клиент не может показать то, чего у него физически нет.

### Delta-снапшоты

Сервер держит для каждого клиента последнее подтверждённое состояние и шлёт
разницу, сжатую zstd. Подтверждение — по номеру снапшота, как в классической схеме
Quake 3 / Source.

Оценка трафика: цель — **не более 20 КБ/с на активного игрока** в разгар боя и
менее 2 КБ/с в спокойном режиме. Мобильный трафик — отдельный бюджет, там
агрессивнее режется частота обновлений.

### Клиентское предсказание

Клиент предсказывает только:

- движение флотов по маршруту (простая интерполяция, сервер всё равно прав)
- немедленный отклик UI на команду

Всё остальное — экономика, бой, осада, технологии — отображается **только по факту
подтверждения сервером**. Никакого спекулятивного применения игровых правил на
клиенте. Это стоит немного отзывчивости и покупает полную невозможность
клиентских читов.

## Протокол

Транспорт: **UDP со своим слоем надёжности**. Нужны и надёжные упорядоченные
каналы (команды, чат, дипломатия), и ненадёжные (позиции флотов, где свежий пакет
важнее потерянного).

QUIC рассматривался и отклонён на старте: это ещё одна крупная зависимость ради
функциональности, которая нам нужна лишь частично. Решение пересматриваемое —
интерфейс `pw_net` спроектирован так, чтобы транспорт можно было заменить.

Пакеты — версионированные схемы, **генерируемые из того же описания, что и
таблицы баланса** (см. [04](04-EDITOR-AND-TOOLS.md)). Сериализатор не пишется
руками и не может рассинхронизироваться со структурами.

Gateway ограничивает частоту команд на игрока. Это дешёвая защита от ботов и от
DoS-нагрузки, и она ничего не отнимает у честного игрока: бой автоматический,
экономика работает через губернаторов — быстрая отправка команд не даёт
преимущества.

## Персистентность

**Что хранится:**

- Дельты от процедурного состояния систем
- Состояние империй: ресурсы, технологии, политики, дипломатия
- Флоты и их составы
- Журнал команд

**Чего не хранится:** всё, что генератор восстановит из сида.

**Восстановление после сбоя.** Снапшот состояния региона раз в N минут плюс журнал
команд между снапшотами. Падение ноды → поднимаем из последнего снапшота и
проигрываем журнал. Симуляция детерминирована, поэтому воспроизведение
гарантированно даёт то же состояние — то же свойство, которое обеспечивает реплеи
и валидацию боёв.
